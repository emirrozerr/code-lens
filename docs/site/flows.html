Core Flows

Five sequence diagrams covering the system's most important paths: indexing a repository, answering a chat question, an AI agent querying the graph over MCP, logging in, and incremental re-indexing. Each diagram is followed by a short step-by-step explanation.

1 · Repository Ingestion (codelens ingest)

Parsing a repository in memory and loading it into Neo4j, optionally followed by domain clustering. This is also what the REST API runs as a background task when a repo is added. 

sequenceDiagram
    actor User
    participant CLI
    participant Indexer
    participant Parser as Java/Python Parser
    participant N4 as Neo4jClient
    participant Neo4j
    participant DC as DomainClusterer
    participant Groq
    User->>CLI: codelens ingest repo --clear --cluster
    CLI->>Indexer: index_repository(repo)
    Indexer->>Indexer: _discover_files() skip build/hidden
    loop each .java / .py file
        Indexer->>Parser: parse_file()
        Parser-->>Indexer: ParseResult (nodes, edges)
    end
    Indexer->>Indexer: _resolve_calls() unresolved to uid
    Indexer-->>CLI: combined ParseResult
    CLI->>N4: clear_database() [--clear]
    CLI->>N4: setup_schema() constraints + fulltext
    CLI->>N4: ingest_parse_result(result)
    N4->>Neo4j: MERGE nodes (batched UNWIND)
    N4->>Neo4j: MERGE edges (mark :Unresolved)
    N4->>Neo4j: DELETE orphan :Unresolved
    CLI->>DC: run_clustering() [--cluster]
    DC->>Neo4j: fetch Class/Function/Interface + edges
    DC->>DC: Louvain best_partition
    loop each cluster (size >= 2)
        DC->>Groq: name + summarise members
        Groq-->>DC: NAME / SUMMARY
    end
    DC->>Neo4j: MERGE :Domain + IN_DOMAIN edges
Ingestion: parse → resolve calls → load graph → cluster into domains.
  1. Discover all .java and .py files in the repo, skipping build directories and hidden paths.
  2. Parse each file through the appropriate Tree-sitter parser, producing CodeNode and CodeEdge objects.
  3. Resolve call targets by name, mapping unresolved calls to stable UIDs.
  4. Optionally clear the existing database (--clear) before loading.
  5. Create schema constraints and a fulltext index (setup_schema()).
  6. Merge all nodes into Neo4j using batched UNWIND, then merge all edges, marking unresolvable targets as :Unresolved.
  7. Drop any orphan :Unresolved nodes that have no matching target.
  8. Optionally run Louvain community detection (--cluster) and call Groq once per community (size ≥ 2) to produce a name and summary, then write :Domain nodes and IN_DOMAIN edges back into Neo4j.

2 · Chat over the Graph (POST /chat)

The chat endpoint gathers structural context from Neo4j via the MCP tools, then streams an LLM answer over SSE. Every tool call is surfaced to the UI as it happens. 

sequenceDiagram
    actor User
    participant FE as Frontend /ask
    participant API as FastAPI /chat
    participant MCP as MCP tools
    participant Neo4j
    participant Groq
    User->>FE: ask question (persona, domainId?)
    FE->>API: POST /chat (SSE, cookie JWT)
    opt domainId provided
        API-->>FE: tool_call_start get_domain
        API->>Neo4j: fetch domain + members
        API-->>FE: tool_call_end
    end
    API->>API: _extract_keywords(message) up to 3
    loop each keyword
        API-->>FE: tool_call_start search_nodes
        API->>MCP: search_nodes(keyword)
        MCP->>Neo4j: fulltext query
        Neo4j-->>MCP: hits
        API-->>FE: tool_call_end
        API-->>FE: tool_call_start get_code_context
        API->>MCP: get_code_context(symbol)
        MCP->>Neo4j: multi-hop query
        Neo4j-->>MCP: context
        API-->>FE: tool_call_end
    end
    API->>Groq: chat.completions stream (context + history)
    loop each token
        Groq-->>API: delta
        API-->>FE: token event
    end
    API-->>FE: done + [DONE]
Chat: domain + keyword search build context, then a streamed Groq completion.
  1. If a domainId was supplied, fetch the domain node and its members from Neo4j and emit tool_call_start / tool_call_end SSE events to the UI.
  2. Extract up to 3 keywords from the user's message with _extract_keywords().
  3. For each keyword, run search_nodes (fulltext) then get_code_context (multi-hop graph query) to assemble structural context, emitting tool-call events for each.
  4. Stream a chat.completions call to Groq (llama-3.1-8b-instant) with the accumulated context and conversation history.
  5. Forward each token delta to the frontend as a token SSE event, then emit done and [DONE].
If GROQ_API_KEY is unset, or Groq errors, the endpoint falls back to character-streaming the raw graph context it collected.

3 · AI Agent Query over MCP

How an external AI agent (Claude Code, Cursor) pulls structural context through the MCP server. 

sequenceDiagram
    actor Agent as AI Agent
    participant MCP as FastMCP Server
    participant Tool as "@mcp.tool"
    participant N4 as Neo4jClient
    participant Neo4j
    Agent->>MCP: call tool e.g. get_callers(name)
    MCP->>Tool: dispatch(symbol_name)
    Tool->>N4: Neo4jClient() connect
    Tool->>Neo4j: run Cypher query
    Neo4j-->>Tool: rows
    Tool->>Tool: format rows as text
    Tool->>N4: close()
    Tool-->>MCP: str result
    MCP-->>Agent: tool result
MCP query: each tool opens a fresh Neo4j connection, runs one Cypher query, and returns plain text.

All 7 MCP tools (search_nodes, get_code_context, get_callers, get_callees, get_domains, get_domain, get_domain_content) follow exactly this same shape: connect, query, format, close, return a plain string. No state is held between calls.

4 · Login & Route Protection

Authentication spans three layers: the Next.js login page, a Next.js route handler that owns the cookie, the FastAPI backend that verifies credentials, and the Edge middleware that gates protected routes. 

sequenceDiagram
    actor User
    participant Login as /login page
    participant NextAPI as Next /api/auth/login
    participant API as FastAPI /auth/login
    participant Neo4j
    participant MW as middleware.ts
    User->>Login: email + password
    Login->>NextAPI: POST /api/auth/login
    NextAPI->>API: POST /auth/login (proxy)
    API->>Neo4j: get_user_by_email
    API->>API: verify pbkdf2_sha256
    API->>Neo4j: update last_login
    API->>API: encode JWT (sub, email, role, exp)
    API-->>NextAPI: access_token + user
    NextAPI->>NextAPI: set codelens_token cookie (httpOnly)
    NextAPI-->>Login: ok + user
    Login->>Login: redirect by role (/admin or /ask)
    User->>MW: GET /admin/* or /ask
    MW->>MW: decode cookie, check exp + role
    MW-->>User: allow or redirect to /login
Login: the Next.js route handler owns the httpOnly cookie; middleware does a cheap claims check; FastAPI does the real verification.
middleware.ts only decodes the JWT to check presence, structure, expiry, and the role claim — it does NOT verify the signature. Signature verification happens in FastAPI on every API call.

5 · Incremental Re-indexing (codelens watch)

The watcher keeps an in-memory snapshot and syncs only the changed files into Neo4j as you edit. 

sequenceDiagram
    participant FS as File System
    participant H as EventHandler
    participant Q as Queue
    participant D as WatcherDaemon
    participant Indexer
    participant N4 as Neo4jClient
    participant Neo4j
    Note over D: start(): full index_repository to in-memory snapshot
    FS->>H: file created / modified / deleted
    H->>Q: (changed|deleted, path)
    D->>Q: get() + debounce 0.5s + drain
    D->>D: changed minus deleted
    D->>Indexer: index_incremental(snapshot, changed, deleted)
    Indexer-->>D: updated ParseResult
    loop each deleted file
        D->>N4: delete_file_subgraph(path)
        N4->>Neo4j: DETACH DELETE
    end
    loop each changed file
        D->>N4: delete_file_subgraph(path)
        D->>N4: ingest_parse_result(mini)
        N4->>Neo4j: MERGE nodes / edges
    end
Incremental sync: debounce file events, re-parse only what changed, and replace just those files' subgraphs.
